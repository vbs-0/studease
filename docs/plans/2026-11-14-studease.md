# StudEase Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A three-tier system that calculates tuition and fees, applies scholarships and payments, reconciles
student balances, and ships a reproducible synthetic dataset with labelled anomalies and a separate ground truth.

**Architecture:** `frontend/` (React), `backend/` (FastAPI), `database/` (PostgreSQL + Alembic). All money rules
live once in `backend/app/domain/` as pure functions; the generator simulates the year by calling them, the
detectors recompute with them, and the API exposes them.

**Tech stack:** Python 3.12, uv, FastAPI, SQLAlchemy 2 Core, psycopg 3, Alembic, PyJWT, pytest, ruff;
PostgreSQL 14+; React 19, Vite 6, TypeScript 5.8, Tailwind 4, TanStack Query 5, react-router 7, vitest;
nginx, systemd, GitHub Actions.

**Spec:** `docs/architecture.md`. Rule ids (R-FEE-1, R-PAY-2, ...) below refer to it. Read it first.

## Global constraints

- Money is integer paise. No `float` in any money path. Percentages round half up: `(amount * bp + 5000) // 10000`
  where `bp` is basis points.
- As-of date `2026-09-05`; default seed `20261022`; scales `starter` and `full` with the volumes in spec section 6.
- ID formats exactly as in spec section 4. IDs are immutable and zero padded.
- `domain/` imports nothing from `api/`, `datagen/`, `engine/`, SQLAlchemy or FastAPI, and never calls
  `datetime.now()` or `random`.
- Ground truth never appears in an input table or input file. It lives in `data/<scale>/ground_truth/` and
  schema `gt`.
- History is appended, not overwritten: `event`, `ledger_entry`, negative allocation rows for de-allocation.
- Generated files: UTF-8, `\n` newlines, rows sorted by primary key, columns in `schema.py` order.
- Every task ends with `uv run ruff check app tests` and `uv run pytest -q` green, then a commit.
- Commit messages end with the line `Authored-By: vbs-0` and carry no AI attribution.
- Nothing is pushed until the owner names the repository, and never before `scripts/scrub_check.py` passes.
- Security controls S-1 to S-21 in spec section 12 are requirements. Each has a test or a checked config line
  in the task named below.
- SQL reaches the database only through bound parameters. No f-string or `%` formatting inside `text(...)`.
- No secret, password, token, real email address, IP address or host name is committed.

### Task 4: Generator (baseline)

**Files:** Create `backend/app/datagen/{__init__,rand,catalog,people,simulate,generator}.py`,
`backend/tests/datagen/test_generator.py`.

**Produces:** `generator.SCALES: dict[str, Scale]`, `generator.generate(scale: str, seed: int, inject: bool = True)
-> tuple[Dataset, list[dict]]`; `simulate.run(scale, seed) -> Dataset`.

Realism requirements for `people.py` and `catalog.py`:
- GPA: truncated normal, mean 7.2, sd 1.1, range 4.00 to 10.00, two decimals.
- Income band: LOW 28%, MID 45%, HIGH 22%, AFFLUENT 5%. Residency: INTERNATIONAL 8%. Hostel 30%.
  Sports quota 4%. Waivers: STAFF_WARD 1.5%, SIBLING 4%, HARDSHIP 3%.
- Program sizes are uneven (Zipf-like weights), tuition differs by level (UG, PG, DIPLOMA) and by program.
- Payment behaviour mix per invoice: FULL_ON_TIME 46%, INSTALMENTS 22%, PARTIAL 9%, LATE_FULL 12%,
  OVERPAY 4%, NONE 7%; payment methods UPI, CARD, NETBANKING, BANK_TRANSFER, CASH, CHEQUE with a skew
  to UPI; amounts follow from the invoice, dates jitter around due dates.
- Leavers: 3% of enrollments leave; of those roughly a quarter cancel before term start and the rest
  withdraw across the three refund bands.

Simulation order inside `simulate.run` (each step calls `domain/`):
1. masters; 2. enrollments; 3. per term in date order: issue invoices (apply carried credit, R-PAY-3),
judge applications and apply awards, receive payments and allocate, post late fees on due + 8, process
leavers (adjust, de-allocate, refund), refund stale credit (R-PAY-5); 4. derive ledger, balances, statuses
and events; 5. top up payment count by splitting (before step 3 allocation, as part of the plan).

Tests first (run on `starter`, session-scoped fixture):
- [ ] exact volumes: 500 students, 20 programs, 1,500 invoices, 750 awards, 2,500 payments.
- [ ] same seed twice gives equal datasets; a different seed gives a different one.
- [ ] coverage: at least one of each: partial payment, overpayment with unapplied credit, each waiver
  type, withdrawal in each band, cancellation, late fee, unpaid invoice, V2 fee row used.
- [ ] every invoice total equals the sum of its lines; no line is over-allocated; every student's
  `student_balance.balance_paise` equals `ledger.balance` and equals the R-LED-3 identity.
- [ ] every award is at most its eligible fees; at most one award per student and term.
- [ ] Run, fail, implement, pass. `full` must generate in under 60 s. Commit: `feat: seeded baseline generator`.
